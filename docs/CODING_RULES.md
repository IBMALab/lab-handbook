# Coding Rules

These rules keep our research **reproducible, readable and safe**.

---

## 1. Data Policy (most important)

| ✅ Allowed in Git | ❌ Never in Git |
|------------------|----------------|
| Source code (.py, .m) | Patient data, DICOM/NIfTI scans, raw EEG |
| Configs, small CSV samples (< 5 MB, anonymized) | Any personally identifiable information |
| Final small figures | Large datasets, model weights > 50 MB |
| `data/README.md` describing where data lives | Passwords, API keys, tokens, `.env` files |

- Store datasets on **lab storage / shared drive**, and document the path & access steps in `data/README.md`.
- **Large datasets (too heavy for GitHub):** do not upload them. Instead, in `data/README.md` provide:
  - the **link** to the data (shared drive / cloud folder, lab storage path, or public source such as PhysioNet, OpenNeuro, Kaggle)
  - **how to access it** — who to ask for permission, any registration/login, licence or data-use agreement
  - **how to download it and where to place it** locally (e.g. `data/raw/`), with the commands or steps
  - dataset **size, version/date**, and a checksum if available
- Large model weights → shared drive or release assets, linked from README.
- If you accidentally push sensitive data, **tell the PI immediately** — deleting the file is not enough; history must be cleaned.

## 2. Git Workflow

- **Never commit directly to `main`.** Work on a branch, open a Pull Request, request PI review.
- Branch names:
  ```
  feature/cnn-model
  fix/normalization-bug
  exp/learning-rate-sweep
  docs/update-readme
  ```
- **Commit at least once per week**, small and focused commits.
- Commit message format:
  ```
  type: short description (max ~60 chars)
  ```
  | type | use for |
  |------|---------|
  | `feat` | new feature / model |
  | `fix` | bug fix |
  | `exp` | experiment run / results |
  | `data` | data-loading / preprocessing changes |
  | `docs` | README, comments, documentation |
  | `refactor` | code cleanup, no behavior change |

  Examples: `feat: add 1D-CNN for EEG`, `fix: correct sampling rate in filter`

- ❌ No files like `final.py`, `final_v2.py`, `final_REAL.py` — Git keeps the versions.

## 3. Code Style

### Python
- Follow **PEP 8**; format with **`black`**, lint with **`ruff`** or `flake8`.
- `snake_case` for functions/variables, `PascalCase` for classes.
- Every function gets a docstring:
  ```python
  def bandpass_filter(signal, low_hz, high_hz, fs):
      """Apply a Butterworth band-pass filter.

      Args:
          signal (np.ndarray): 1-D input signal.
          low_hz (float): Lower cutoff (Hz).
          high_hz (float): Upper cutoff (Hz).
          fs (float): Sampling rate (Hz).

      Returns:
          np.ndarray: Filtered signal.
      """
  ```
- Use **type hints** where practical.
- Reusable logic in `.py` modules under `code/`; notebooks only for exploration and plots.

### MATLAB
- `camelCase` for functions and variables; one main function per file; file name = function name.
- Header comment block in every function (purpose, inputs, outputs, author, date).
- Avoid `clear all` / `close all` inside functions; no hard-coded absolute paths.

### General
- ❌ No hard-coded paths like `C:\Users\Ali\Desktop\data` — use configs or relative paths.
- ✅ All parameters (learning rate, epochs, filter cutoffs) in `configs/`, not buried in code.
- ✅ Meaningful names: `train_loss`, not `x1`, `temp`, `aaa`.
- ✅ Remove dead/commented-out code before merging.
- Comments explain **why**, not what.

## 4. Reproducibility

- **Fix random seeds** (Python `random`, `numpy`, `torch`/`tensorflow`; MATLAB `rng`).
- Record the environment:
  ```bash
  pip freeze > requirements.txt
  # or
  conda env export > environment.yml
  ```
- Note Python/MATLAB version and GPU/CUDA version in README.
- Every result in your thesis/paper must be reproducible by a script in the repo — note the exact command in README.
- Log experiments (date, config, metrics) — e.g. `results/experiment_log.csv`, Weights & Biases, or MLflow.
- Report metrics as **mean ± std over multiple runs/folds** where applicable.

## 5. Pull Request Checklist

Before requesting review:
- [ ] Code runs from a clean clone
- [ ] No data, credentials or large files added
- [ ] Docstrings / comments added
- [ ] README updated if usage changed
- [ ] Results/figures regenerated by script, not manually edited
